PerfectOutfit — Progress Log

2026-09-18 (3)
- Implemented issue #8 ("Export/import: single schema definition, safe import,
  round-trip test"). ExportImportManager previously defined four hand-written DTOs that
  mirrored the four Room entities field-by-field, spelling each field out three times
  (entity, export mapping, import mapping); import also deleted all four tables before
  parsing had fully validated the file.
  Changes:
    * ClothingItem, WeatherSnapshot, OutfitEntry, OutfitItem, Sport, BodyPart: added
      `@Serializable` directly to the Room entities/enums (core/model). They're now
      serialized as-is instead of through mirror DTOs — each field exists in exactly one
      place. Enum JSON output is unchanged (kotlinx serializes an enum by its `.name`,
      same string `Sport.valueOf`/`BodyPart.valueOf` used to read/write), so the JSON
      shape is byte-for-byte compatible with files the old code produced.
    * ExportImportManager.kt: `ExportData` gains a `version` field
      (`CURRENT_EXPORT_VERSION`, currently 1) marked `@EncodeDefault(...ALWAYS)` so it's
      always written even though it also has a default (needed for old files, which lack
      the key, to still decode). Manager now depends on the four DAOs and a
      `DatabaseTransactionRunner` directly instead of CatalogRepository/OutfitRepository/
      WeatherRepository (acceptable per the issue — those repos are slated for dissolution
      by #9/#10). `importFromJson` decodes+validates the whole file first (a parse or
      unknown-enum-constant failure now throws before any delete runs), then does the
      delete-then-insert inside one `transactionRunner.runInTransaction { }` block.
    * DatabaseTransactionRunner.kt (new interface) / RoomTransactionRunner.kt (new,
      `AppDatabase.withTransaction`) / core/di/DatabaseModule.kt (new `@Binds`): same
      interface-plus-Android-adapter seam issue #6 used for RatingReminder, so the
      round-trip test can run on the plain JVM instead of needing Robolectric for a real
      Room transaction.
    * CatalogRepository/OutfitRepository/WeatherRepository: removed the getAll/insertAll/
      deleteAll pass-through methods that existed only for ExportImportManager and are now
      unused.
    * Moved FakeOutfitEntryDao/FakeOutfitItemDao from core/notification (app/src/test) to
      a new shared app/src/test/.../testutil package per the issue's suggestion, since
      export/import needed them too; gave FakeOutfitItemDao working implementations
      instead of UnsupportedOperationException (nothing tested the throwing versions).
      Added FakeClothingItemDao, FakeWeatherSnapshotDao, FakeDatabaseTransactionRunner
      (runs the block inline, no real transaction) alongside them.
    * ExportImportManagerTest.kt (new): round-trip test (export through fakes, import into
      fresh fakes, assert all four tables equal), a test that a malformed JSON string
      leaves the seeded fakes untouched, a test that a hand-written fixture in the old
      (pre-#8, no "version" key) shape still imports correctly, and a test that exported
      JSON contains the version key.
    * CONTEXT.md: added an "Export/import schema" glossary entry.
  Verified: ./gradlew testDebugUnitTest and ./gradlew assembleDebug both succeed (Hilt
  graph resolves with the new DatabaseModule @Binds, Room accepts the @Serializable
  entities). Did not manually verify export/import on-device (no emulator in this
  environment) — worth a quick manual round-trip check, and specifically confirming an
  old on-disk backup file (from before this change) still imports.

2026-09-18 (2)
- Implemented issue #7 ("Weather warning thresholds in one place; remove dead warning
  path and unreferenced code"). Three different answers to "when is this hour's UV/wind/
  rain concerning" (mapper warnings, Home screen's warning cards, WeatherStatusColors'
  bands) now come from one place, plus removal of dead code the issue identified.
  Changes:
    * WeatherSeverity.kt (new, feature/home): WeatherSeverity enum (NONE/NOTABLE/HIGH)
      and WeatherThresholds object, the single source of truth for UV, wind, and rain
      bands. UV HIGH is >= 5 (the threshold already visible on the Home screen from issue
      #1), not the mapper's unused >= 4. Wind HIGH is >= 20 km/h. Rain HIGH is >= 50%.
    * HomeScreen.kt: UV/wind warning cards now check
      WeatherThresholds.___Severity(...) == WeatherSeverity.HIGH instead of inlined
      `>= 5` / `>= 20.0` literals.
    * WeatherStatusColors.kt: uvStatusColor/windStatusColor/rainStatusColor now derive
      their good/moderate/severe color from WeatherThresholds instead of their own
      separate band literals, so color and warning-card severity can never disagree again.
    * WeatherMapper.kt: removed hasRainWarning/hasUvWarning/hasWindWarning (dead — their
      only caller was the HomeUiState.warnings field, also removed, which no screen read).
    * Deleted dead code identified in the issue: ui/components/WarningBanner.kt,
      ui/components/WeatherCard.kt (both unreferenced), HomeViewModel.selectHour /
      setAdjustedTemp / saveWeatherForLater (no callers), WeatherRepository.fetchWeatherOnly,
      CatalogRepository.getItemsBySportAndBodyPart, OutfitEntry.bHasRating (all unused),
      and the ExampleUnitTest.kt / ExampleInstrumentedTest.kt template leftovers.
    * WeatherThresholdsTest.kt (new): unit tests for every band boundary, pure JVM, no
      Android — same style as HourlyWeatherTest.kt.
    * CONTEXT.md: added a "Weather severity" glossary entry documenting the module and
      why UV HIGH is 5 and not the WHO-standard 6.
  Verified: ./gradlew testDebugUnitTest and ./gradlew assembleDebug both succeed. Did not
  manually verify the Home screen's UV/wind warning cards on-device (no emulator in this
  environment) — the threshold values are unchanged from what was already shown, so no
  visible behavior change is expected; worth a quick manual confirmation.

2026-09-18
- Implemented issue #6 ("Rating reminder seam: make ViewModels and outfit logging
  testable without Android"). First hand-written DI seam in the app: previously every
  interface was generated (Room DAOs, Retrofit) and everything else was a concrete
  @Singleton, which is why none of the six ViewModels had a unit test.
  Changes:
    * RatingReminder.kt (new): interface with exactly two methods, show(outfitEntryId,
      sport, dateMs, durationHours) and cancel(outfitEntryId) — nothing else about
      notifications leaks through it.
    * AndroidRatingReminder.kt (new, replaces NotificationHelper.kt): same notification
      behaviour (channel, deep link, three quick-response actions) as an adapter for the
      new interface. Channel creation moved out of the constructor (`init {}`) to a
      `channelCreated` flag checked lazily on first show(), so constructing the adapter
      now has no side effects.
    * FakeRatingReminder.kt (new, app/src/test): recording fake storing every show/cancel
      call for assertions.
    * core/di/NotificationModule.kt (new): first @Binds module in the app
      (@InstallIn(SingletonComponent::class) abstract class), binds RatingReminder to
      AndroidRatingReminder.
    * HomeViewModel.kt, RateOutfitViewModel.kt: inject RatingReminder instead of the
      concrete NotificationHelper.
    * RatingActionHandler.kt: now injects RatingReminder and routes the cancel through
      it instead of calling NotificationManagerCompat.from(context).cancel(...) directly.
      Removed the public mutable `mainDispatcher` var — RatingActionHandlerTest now uses
      kotlinx-coroutines-test's Dispatchers.setMain(UnconfinedTestDispatcher()) instead of
      swapping in a custom dispatcher field. Kept RateOutfitActionReceiver's internal
      `beginAsyncWork()` hook: it exists for a different, unrelated problem (Robolectric
      cannot supply a real goAsync() PendingResult), not for the notification seam.
    * build.gradle.kts / libs.versions.toml: added kotlinx-coroutines-test as a test
      dependency for this and future ViewModel tests.
    * CONTEXT.md: added a "Rating reminder" glossary entry.
  Verified: ./gradlew testDebugUnitTest and ./gradlew assembleDebug both succeed (Hilt
  graph resolves with the new @Binds module). Could not manually verify the on-device
  notification/deep-link in this environment (no emulator) — worth a quick manual check.

2026-07-27
- Added quick-response rating buttons ("Too cold" / "Perfect" / "Too hot") to the
  post-workout rating reminder notification, so a rating can be logged without opening
  the app.
  Design (via /grill-me interview): buttons added to the existing reminder notification
  (NotificationHelper.kt) rather than a new one; tapping a button cancels the notification,
  saves the rating (last-write-wins, no-op if the entry was deleted), and shows a brief
  confirmation Toast.
  Changes:
    * NotificationHelper.kt: showRatingNotification() now adds three NotificationCompat.Action
      buttons, each a PendingIntent.getBroadcast targeting RateOutfitActionReceiver with a
      distinct data URI (perfectoutfit-rate://<entryId>/<rating>) so the three actions and the
      existing content intent never collide.
    * RateOutfitActionReceiver.kt (new): @AndroidEntryPoint BroadcastReceiver, exported=false,
      registered in AndroidManifest.xml. Validates the intent via RatingActionValidator, then
      uses goAsync() + a coroutine to delegate to RatingActionHandler before calling finish().
    * RatingActionHandler.kt (new): the actual async logic (cancel notification, call
      OutfitRepository.rateEntry(), show toast) factored out of the receiver into a plain
      injectable class. Kept separate because coroutines launched directly inside the
      Hilt-transformed receiver hung under Robolectric's sandboxed classloader in testing;
      delegating to a plain class sidesteps that and is independently unit-testable.
    * RatingActionValidator.kt (new): pure entryId/rating validation, no Android dependencies.
    * strings.xml: added rating_saved_toast.
    * Added Robolectric + androidx.test:core as test dependencies (build.gradle.kts,
      libs.versions.toml) to unit-test the receiver and handler.
